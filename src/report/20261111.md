# 20261111 开发周报：通过 ostool 让 RT24 核心运行自定义固件

> **说明：这是移植 RME 之前的一次随意测试。**
> 本次只验证「ostool 能不能把自定义固件送到 RT24 并跑起来」，
> 方案以最短路径跑通为准，不是最终架构。

---

## 一、目标与术语

本次目标是：用 `ostool` 一条命令上板，让 K3 的 RT24 实时核执行我们自己的固件，
并能看到 RT24 的输出。

先统一本文涉及的几个名字：

| 名称 | 含义 |
|---|---|
| **AP** | K3 的 **X100 大核（hart0）**，U-Boot `bootm` 后运行在 S-mode |
| **RT24** | RT24 实时核（rcpu0），有独立的私有 DDR 和固定启动入口 |
| **RT24M** | 运行在 RT24 上的 M-mode 固件，负责引导和最小 M 态环境 |
| **RT24S** | 运行在 RT24 上的 S-mode 固件，也就是本次要运行的自定义固件 |
| **共享窗** | AP 与 RT24 都能访问的片上 SRAM，地址 `0xC0800000` |

厂商默认由 U-Boot 的 `k3-rproc.c` 从 `esos.itb` 里取 ELF 启动 RT24。
本次不依赖这条路径，改为：

- ostool 只负责把 **AP 固件**下载到板子并启动；
- **AP 固件自己**完成 RT24 固件的拷贝、启动和日志转发。

---

## 二、整体链路

```text
PC
 │  ostool board run
 │  ├─ make 构建 AP 固件（内嵌 RT24M / RT24S 镜像）
 │  ├─ 打包 FIT image
 │  └─ 通过 TFTP / U-Boot shell 下载并 bootm
 ▼
U-Boot（S-mode）
 │  bootm 0x140000000
 ▼
AP 固件（X100/hart0，S-mode，链接/加载 0x102200000）
 │  1. 把 RT24M、RT24S 两个镜像分别拷到 RT24 私有 DDR
 │  2. 写 RCPU 寄存器，解除复位并唤醒 RT24
 │  3. 轮询握手
 │  4. 把 RT24 写进共享内存的日志转发到 UART0
 ▼
RT24M 固件（M-mode，链接/加载 0x100200000）
   1. 写自己的 BOOT_ENTRY_LO = 1，完成握手
   2. 初始化栈、mtvec
   3. 配置 PMP
   4. mret 到 S 态物理入口 0x100300000
 ▼
RT24S 固件（S-mode，链接 0xFFFFFFC100300000 / 加载 0x100300000）
   1. 从物理入口启动，自己构造 Sv39 根表并打开 satp
   2. 跳到高半区执行自定义逻辑
   3. 通过 ecall(SVC_PUTCHAR) 交给 M 态打印
```

最终是 **三个固件** 接力：

```text
ostool → ap.elf → rt24m.bin → rt24s.bin
```

---

## 三、三个固件与地址

| 固件 | 运行核/特权级 | 链接地址 | 加载地址 | 作用 |
|---|---|---|---|---|
| `ap.elf` | AP（X100/hart0，S-mode） | `0x102200000` | `0x102200000` | RT24 加载器 + 日志转发器 |
| `rt24m.bin` | RT24（rcpu0，M-mode） | `0x100200000` | `0x100200000` | 握手、PMP、进入 S 态、打印服务 |
| `rt24s.bin` | RT24（rcpu0，S-mode） | `0xFFFFFFC100300000` | `0x100300000` | 自定义 S 态固件 |

`rt24s` 的链接地址不是物理地址，而是 Sv39 高半区虚拟地址：

```text
VA = PA + 0xFFFFFFC000000000
```

这一点必须和 RT24S 自己建立的页表一致。

## 四、正确加载 RT24 固件的步骤

### 1. 两个 RT24 固件链接到正确地址

```ld
/* rt24m：链接地址 = 加载地址 */
. = 0x100200000;

/* rt24s：链接在高半区，物理加载到 0x100300000 */
. = 0xFFFFFFC100300000;
```

RT24S 在打开 `satp` 之前运行在物理地址上，因此启动代码必须使用
PC 相对寻址，并在访问链接符号时减去 `0xFFFFFFC000000000`。

### 2. 把两个 RT24 镜像内嵌进 AP 固件

不要让 ostool 单独传三个文件，直接让 AP 固件带上两个 RT24 镜像：

```asm
rt24m_bin_start:
    .incbin "rt24m.bin"
rt24m_bin_end:

rt24s_bin_start:
    .incbin "rt24s.bin"
rt24s_bin_end:
```

镜像较大时不要转成 C 数组，否则源码会膨胀到几十 MB。

### 3. AP 把两个镜像分别拷到 RT24 私有 DDR

```c
ap_memcpy((void *)0x100200000, rt24m_bin_start, rt24m_size);
ap_memcpy((void *)0x100300000, rt24s_bin_start, rt24s_size);
```

拷完必须做 cache 写回：

```c
win_flush(0x100200000, (rt24m_size + 63) & ~63UL);
win_flush(0x100300000, (rt24s_size + 63) & ~63UL);
```

否则 RT24 可能读到陈旧或半截代码，表现为偶发起不来。

### 4. load 和 start 必须分开

- **load 阶段**：让 RT24 保持「复位 + 休眠」，只做镜像拷贝；
- **start 阶段**：镜像和 cache 都准备好后，再解除复位、唤醒。

如果提前唤醒，核可能在镜像还没拷完时就开始取指。

> 这里的 load/start 流程与寄存器顺序参考 U-Boot 源码
> **`drivers/remoteproc/k3-rproc.c`**，对应函数是
> `k3_rproc_load()` 和 `k3_rproc_start()`（core0 分支）。

### 5. 写正确的 RCPU 寄存器

| 寄存器 | 地址 | 作用 |
|---|---|---|
| `PMU_AUDIO_CLK_CTRL` | `0xd428294c` | 解除 APMU 复位、等时钟稳定、释放系统复位 |
| `RCPU_EXECUTION_CTRL` | `0xc088c030` | 置 1，允许 RT24 执行 |
| `RCPU_CORE0_BOOT_ENTRY_LO/HI` | `0xc088007c / 0xc0880080` | 启动入口 `0x100200000` |
| `RCPU_CORE0_HART_ID_SET` | `0xc0880084` | 写 hartid = 0 |
| `RT24_CORE0_SW_RESET_REG` | `0xc088c0cc` | 0=保持复位，1=解除复位 |
| `RT24_CORE0_SW_WAKEUP_REG` | `0xc088c0d4` | 0=保持休眠，1=唤醒 |

`BOOT_ENTRY` 是 64 位地址，`LO` 和 `HI` 都要写。入口先指向 RT24M
（`0x100200000`），由 RT24M 再进入 RT24S。

### 6. 握手

RT24M 起来后把自己的 `BOOT_ENTRY_LO` 改写成 `1`：

```c
*(volatile unsigned int *)0xc088007c = 1;
```

AP 轮询该寄存器，读到 `1` 即认为 RT24 已经跑起来。

轮询前必须 `cbo.inval` 该地址所在 cache 行，否则 AP 可能一直读到自己
cache 里的旧入口地址。

### 7. M 态配置 PMP 并进入 S 态

RISC-V 规定没有 PMP 项命中时 S/U 态访存失败。RT24 复位后 PMP 为空，
所以 M 态必须先放行整个地址空间：

```c
csrw pmpaddr0, ~0UL
csrw pmpcfg0,  0x0f     /* TOR, R/W/X */
```

然后设置 `mstatus.MPP = S`、`mepc = 0x100300000`，执行 `mret`。
进入 S 态时保持 `satp = 0`，让 RT24S 从物理入口开始执行。

### 8. RT24S 自己构造 Sv39 页表

页表由 S 态构造，和 RME 的做法一致。RT24S 的 `_start` 做四件事：

1. 用物理地址设置栈、清 `.bss`；
2. 构造根表；
3. 写 `satp`、执行 `sfence.vma`；
4. 跳到高半区继续执行。

根表只放两个 1G 大页叶子，和 RME 的
`__RME_RV64V_Pgt_Boot_Init()` 保持同构：

```text
identity  ：VA 0x1_0000_0000        -> PA 0x1_0000_0000
high-half ：VA 0xFFFFFFC1_0000_0000 -> PA 0x1_0000_0000
```

对应：

```c
Root[KPGT_PA >> 30]         = leaf;
Root[256 + (KPGT_PA >> 30)] = leaf;
```

identity 叶子保证打开 `satp` 后当前物理 PC 还能继续执行；
跳过高半区后，代码和数据都使用 `VA = PA + 0xFFFFFFC000000000`。

根表由 RT24S 在运行时构造，放在共享 SRAM（日志环之后）：
`0xC0802000`。这个地址不与日志环（`0xC0801000`）重叠。
共享 SRAM 的写入对 RT24 侧直接可见，日志环已经验证过这条路径，
因此 MMU 打开后能立即读到刚写好的页表。

不要用普通 store 把页表写进 BSS 就直接开 `satp`：MMU 页表 walker
不保证能看到 D-cache 中尚未回写的页表项，实测会在 `sfence.vma` 处
直接 instruction page fault。

### 9. 如何判定 MMU 真的生效

验证不能只看 `satp` 的 mode 位，要同时覆盖取指、数据翻译和权限检查：

1. **取指**：打开 `satp` 后，S 态从高半区地址继续执行。
   如果翻译没生效，高半区地址会直接跑飞。
2. **正向别名**：经 high-half VA 写一个值，再经 identity VA 读回，
   两者一致说明两个窗口指向同一物理页。
3. **反向别名**：经 identity VA 写另一个值，再经 high-half VA 读回，
   证明两个方向的翻译都成立。
4. **取指翻译**：把函数的 identity 地址算出来并调用，能正常返回说明
   取指也经过页表翻译。
5. **权限检查**：读未映射地址 `0x30000000`，必须触发
   **load page fault（mcause=13）**，且 `mtval=0x30000000`。
   不接受 access fault（mcause=5/7）：那可能是 PMP 或权限问题，
   不能证明地址翻译生效。

### 10. 输出走共享内存日志环

RT24S 不直接写串口，也不直接写日志环；它通过 ecall 调用
`SVC_PUTCHAR`，由 M 态写共享 SRAM 的日志环。RT24S 对共享 SRAM 的
唯一写入是前面构造的页表（`0xC0802000`），与日志环互不干扰。

```text
共享窗基址：0xC0800000
日志环偏移：+0x1000

+0x000  head
+0x040  data[1024]
+0x440  tail
```

M 态写数据，AP 轮询后转发到 UART0。AP 是唯一操作 UART 的核。

打印按**单字符服务**实现，而不是一次传一个字符串。这样做的好处是：
M 态只接收一个字节，不需要知道 S 态当前的地址空间，也不需要替 S 态
做 VA→PA 换算；S 态无论用 identity、高半区还是以后更复杂的页表，
打印接口都不需要改。

## 五、ostool 配置

### `ostool-build.toml`

```toml
[system.Custom]
build_cmd = "true"
elf_path = "build/ap.elf"
to_bin = true
```

### `ostool-board.toml`

```toml
board_type = "BananaPi"

kernel_load_addr = "0x102200000"
fit_load_addr = "0x140000000"
bootm_addr = "0x140000000"

timeout = 120

uboot_cmd = [
    'setenv netretry no && setenv autoload no && dhcp && setenv autoload yes',
]

[[shell_check_steps]]
success_regex = ["RT24 BOOT OK"]
fail_regex = ["(?i)panic", "(?i)TRAP", "NOT ALIVE", "RT24 FAIL"]
```

### 运行脚本

在仓库根目录执行：

```bash
#!/bin/bash
set -e

make
exec ostool board run --config ostool-build.toml --board-config ostool-board.toml
```

所有常规日志都带固定前缀：

- AP 行：`AP: ...`
- M 态行：`RT24M: ...`

## 七、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| RT24 起不来 | 镜像拷贝后没有 cache 写回 | 拷贝完执行 `cbo.flush` |
| AP 一直等不到握手 | 轮询前没 `cbo.inval` | 失效 `BOOT_ENTRY_LO` 所在 cache 行 |
| 最后一批日志丢失 | `head` 发布后没有再 fence | 写 `head` 后补一次 `fence` |
| S 态一进去就 access fault | 复位后 PMP 为空 | M 态配置 PMP 放行 S/U 访存 |
| 打开 satp 立刻缺页 | 页表写在 BSS，MMU 读到未回写的页表 | 在共享 SRAM 中构造根表，写入对 RT24 直接可见 |
| 第一次异常就跳飞 | `mtvec` 未 4 字节对齐 | trap 入口加 `.balign 4` |
| ostool 提前判成功 | `success_regex` 指向首行 | 用最终成功标记 `RT24 BOOT OK` |

## 八、小结

这次随意测试验证了一件事：

> **ostool 不必理解 RT24。它只需要启动 AP 固件；AP 固件负责把
> `rt24m` 和 `rt24s` 两个镜像都加载到 RT24，先跑 M 态，再进入 S 态。**

`rt24s` 运行在 Sv39 高半区，根表只放 identity 和 high-half 两个 1G
大页叶子。打印统一走单字符 `SVC_PUTCHAR`，AP 是唯一操作 UART 的核。

本次已经按这条路径完成验证：ostool 启动 AP，AP 加载 RT24M 和 RT24S，
RT24S 建立 Sv39 页表并正常运行在 RT24 核上。
